Stamped-pattern editor, web app first. Commercial product. The repo is PUBLIC while it is developed (since Oct 11 2026) and goes private again before it is sold: see "Public repo rules" below and docs/public-repo.md.

## Commands
npm run build | dev | check:platform | test | test:build | test:update-golden | test:webkit | perf | coupling-map
Source of truth for the app is src/: ES modules in src/modules (order in manifest.json), start-up in src/main.js, page in src/shell.html. `npm run build` bundles them into dist/wodblok.html plus an identical dist/index.html for hosting (no bundler dependency); `npm run dev` serves the unbundled modules at http://127.0.0.1:5199/ (test them with WB_TARGET=esm). (`legacy/` holds the old v100 file; no test uses it any more.)

## Never break (what the app must always be)
- No explanatory text or tooltips in panels. At launch the Default workspace opens its tool windows (the first workspace if none is called Default; none if there are no workspaces). The template picker (New from template) also opens at launch unless Settings > General > Templates at launch is off. Launch fully cleared. Tests start with no workspaces saved and the picker off (tests/helpers/harness.js), so they still see an empty launch unless a test asks for them (`workspaces: true`, `templates: true`).
- UI follows docs/developing-wodblok.md Part 9 (the UI standard; tokens and scales, one component per role, and one folder tree for every library). Do not invent a size, radius, colour, duration or list design; if the scale lacks something, ask and change the guide first.
- Speed first: run `npm run perf` before committing anything that touches drawing, dragging or sliders. No perf regression over 10%.
- No backwards compatibility (owner, Oct 18 and 19 2026): a project file or template made by an older WODBLOK is refused with a message and never converted; there is no migration code. A file from a newer app still opens read-only and is never rewritten.
- Platform access only through src/platform/. User actions are commands in the registry. The document is plain data with stable ids. No runtime network, with one exception: `src/platform/account.js` may talk to the app's own host (`/api/me`, `/api/usage`, `/api/feedback`, `/api/gate-cookie`, docs/accounts.md) and makes no request from a file or a local dev server (`npm run check:platform` fails on `fetch` and friends anywhere else). Fonts bundled. Usage tracking is active-time totals per day for early_access and tester accounts only, never anything from a project or a file; nothing on the drawing or dragging path. Pointer events; nothing hover-only in new code. No alert/confirm/prompt.
- Modules export functions and do no work on import; start-up order lives in src/main.js.
- Ask before adding a dependency. Licences: MIT, BSD, ISC, Apache, OFL.
- Snapshots and golden screenshots: never update them just to make tests pass. **Pixel goldens** (`tests/__golden__/`): when a full-suite run fails some, look at each diff; if it is exactly the change this release made on purpose (new labels, text size, layout, a new control), regenerate those goldens (`--update-snapshots=changed` on just those tests, then re-run them), and say in the report which ones and why. A golden that fails for a reason the release does not explain is a bug: fix it or ask, never regenerate it. **State and SVG snapshots** (`tests/__snapshots__/`) still need the user's approval first: say which changed and why, and ask.
- Desktop (Mac/Windows) and mobile are later; do not build them now, but do not block them.

## Public repo rules (while the repo is public)
Treat everything pushed as published: it can be cloned and forked at once, and making the repo private later does not remove copies.
- Never commit secrets (keys, tokens, passwords), the user's email or phone, local file paths, or personal files. Check `git diff --cached` for these before every commit.
- Test fixtures (`tests/fixtures/`) must be made-up sample projects or ones the user has approved as public. Never add the user's real project files, artwork, imported fonts or stamp library exports without asking first.
- No third-party artwork, fonts or code without a licence that allows publishing (MIT, BSD, ISC, Apache, OFL).
- No licence file and no "open source" wording: the code stays all-rights-reserved. Do not add a README that invites contributions or copies.
- Never add anything that identifies the user personally (name, address, accounts) beyond the git commit author.
- wodblok.com is hosted on Cloudflare from `main` and is currently open to anyone who visits (no login), so the whole built app is already downloadable by visitors. Never put anything in the build that must stay secret (no keys, no personal data, no real project files in the app). Do not link wodblok.com anywhere public. Putting the site behind Cloudflare Access, or blocking search engines, is the user's decision: never do it unasked. The user has accepted (Oct 11 2026) that anyone who finds the site may use it for now, so do not raise it again unless they ask or the situation changes (selling starts, a paywall is built). **Update Oct 17 2026:** the user asked for accounts. 1.20.0 adds sign-in (Clerk) and an approval gate for the hosted app (docs/accounts.md); it is OFF until `GATE_HOSTS` is set in Cloudflare, so merging it changes nothing by itself. The gate protects the hosted copy only: while the repo is public the source is still readable. Keys, tokens and the Clerk secret key never go in the repo (only the Clerk *publishable* key, which is public by design).
- Before the user makes the repo private again, follow the checklist in docs/public-repo.md. Never delete the repo, change its visibility, or rewrite git history without the user asking for that specifically.
- GitHub Actions on a public repo are free, but keep the lean workflows (docs/ci-budget-rules.md) in case the repo goes private again.

## Release workflow
1. **Check the version first.** At the start of every session, fetch, state the newest version on `main` (package.json) and the latest tag, and work from that, never from an older checkout or branch. Older versions and `legacy/` are never touched, rebuilt, archived or modified unless the user explicitly says so.
2. **Branch.** Work on `fix/<version>-<name>` (or `feat/...`), never on `main`. Keep releases small (one theme, a few items) so a revert undoes little. One commit per behaviour change, each with a test (renames and CSS-only changes may share one commit and one test).
3. **Test, scaled to the risk.** Run the quick tests that touch the change (under a minute or two) and `npm run perf` where the Never-break list says so. Run the full suite only for risky changes, only when the owner says so, and when suggesting it give the importance percentage with one sentence of why; "the suite" means the CI shard suite (PR ready: four Chromium shards, WebKit, picture comparison), not a slow local run. Importance guide: about 60-90% importance for drawing, rendering, Randomize, saving and opening files, the file format or anything in src/platform; 30-50% for shared code such as history, panels or the document. Below that, quick tests are enough. **Never start the full suite or CI unless the owner says so for that release (owner, Oct 19 2026: it wastes a lot of time).** CI (.github/workflows/test.yml) runs the editor suite (four Chromium shards, picture comparison, WebKit) only when started by hand (Actions > tests > Run workflow) or on a pull request labelled `run-suite`; opening, pushing to or marking a pull request ready does not start it, and the skipped jobs still satisfy the required checks. GitHub Actions minutes are limited (docs/ci-budget-rules.md): never add workflows that run on every push, never use macOS or Windows runners outside release builds, and keep a new push from restarting a run (concurrency cancel).
4. **Version and docs.** Bump package.json and the lockfile (the version is MAJOR.MINOR.PATCH; the build writes it into WB_VER, the badge and <title>; 1.0.0 shows as v1.0, 1.2.1 as v1.2.1). Each release raises the minor, a hotfix raises the patch, the major changes only when the user says so (2.0.0 ended the layer update). A plan made of several steps numbers each step as a patch (2.0.1, 2.0.2...) and raises the minor once, when the plan is done. One git tag per release (made by the tag workflow). Write the release's outcome in docs/plan.md.
5. **Preview.** After each push that is not docs- or tests-only, rebuild (`npm run build`, from the clean commit so the bottom-bar stamp is the commit date) and publish dist/wodblok.html to the preview artifact (https://claude.ai/artifact/Y7qKSU4gbU9sCdQYNmBH93, same URL, same capabilities) without being asked.
6. **Report, once, in one short block:** a task list with approximate % complete; what was and was not run; the importance of the full suite as a percentage with one sentence of why (if it was not run); any snapshot or golden that changed (ask before updating).
7. **Going live.** `main` is hosted on Cloudflare: whatever lands on `main` is live on wodblok.com. Merging into `main` is called "going live". Never go live without the user saying so for that release. Say before going live if the release touches saving, opening files or the file format. To undo a release, see docs/going-live.md.

## Tests
- Tests run on the built app (`dist/wodblok.html`, run `npm run build` first); `WB_TARGET=esm` runs them on the unbundled modules from `npm run dev`. The three sample projects in `tests/fixtures/` are made up (tests/fixtures/make-fixtures.js).
- Tests drive the real UI and use only these hooks: the page's `window.__wbTest = { state(), commands, ... }` (`state()` is the JSON of the document, `commands` is the command registry for the commands tests).
- Determinism: seeded Math.random, fixed Date, no network, fixed viewport and locale. All injected from the test side; the app is not modified.
- Three layers of checks: document state (`tests/__snapshots__/**/*.state.json`), SVG markup summary (`*.svg.json`), pixels (`tests/__golden__/<WB_ENV>/`, only valid in the environment that made them; set `WB_PIXELS=0` to skip them).
- Coupling map of the single-file code: docs/coupling-map.md (`npm run coupling-map`, mapped from the built app).
